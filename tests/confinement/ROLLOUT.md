# Future scoped rollout and rollback — not executed

No production service or configuration was changed by this investigation. There is therefore no live rollback to perform. The candidate is an artifact for a separately authorized native-service confinement project, not permission to restart OpenCode or Bridge.

Before any installation:

1. Build an immutable, root-owned runtime image with a pinned OpenCode binary/loader/library closure and a fixed reviewed bootstrap. Do not bind the whole host `/usr`, `/etc`, `/run` or `/var/lib`. Identify required CA trust, DNS, toolchain, Git configuration, state/cache and provider dependencies individually. No production credential/session copying into testing.
2. Use a dedicated service identity. Separate native tool execution from API/provider credentials and credential-bearing parent processes. Same-UID tools and a server credential cannot be isolated merely by filesystem path hiding. Resolve inherited descriptor/environment and proc access.
3. Select either a private PID namespace or another verified proc confinement implementation. The review-only systemd255 example hides `/proc` and is not behaviorally equivalent to the fixture. Validate Bun/OpenCode compatibility on independent synthetic state. Do not silently expose host proc to fix startup.
4. Validate AF_UNIX/tool compatibility and explicit network egress policy. Offline mode cannot supply the current Bridge/API/provider flow without a separately approved transport design. Do not add network plumbing as part of this artifact.
5. Test the exact packaged service on an independent host, synthetic credentials/state/workspace and no public route; repeat denied paths, symlink/hard-link/import cases, other identities, proc/fd access, network/socket cases and positive builds. Test startup failure without automatic retries. The missing bootstrap/rootfs and current credential boundary make live deployment NO-GO.
6. Obtain separate authorization for affected native-service lifecycle/configuration changes. Before any future maintenance, quiesce clients, reconcile every known accepted execution using private ledgers and positive terminal evidence, preserve history digests, retain the original single-writer lock identity and enforce ADR-010/011. Unknown work stops maintenance. This project does not modify ACLs or enable a second writer.

Under that future authorization, record exact original unit/drop-in files, image/binary digests, UID, mount paths, credential interface and process identities. Add only one named candidate drop-in and fixed reviewed runtime image. Validate with `systemd-analyze verify` and offline acceptance first. A condition marker is an additional accident guard, not authorization. Never delete/recreate writer lock files or change the original root OpenCode instance.

Scoped rollback: keep clients fenced; reconcile any accepted work before another stop. Remove only the newly introduced confinement drop-in/marker and restore exactly the prior native unit/configuration under that future approval. Do not restore an old native database/history, rotate secrets, widen ACLs, change routing or swap Bridge binaries. Preserve native state, history and lock identities. Do not auto-retry a failed startup. If evidence cannot justify a safe native restart, remain blocked and preserve evidence instead of improvising. Deleting the local prototype worktree is the only cleanup relevant to the present investigation.
